# Практическое занятие 1. Разработка структуры проекта и модульной структуры программного решения

**МДК:** 02.02 «Инструментальные средства разработки программного обеспечения»  
**Продолжительность:** 4 часа  
**Форма:** практическое занятие  
**Основной стек:** C# / .NET 9, Git

## 1. Цель

Научиться проектировать структуру репозитория и модульную структуру программного решения, определять ответственность проектов .NET, настраивать допустимые зависимости и подтверждать воспроизводимость сборки и тестирования.

## 2. Планируемые результаты

После выполнения студент должен уметь:

- выделять модули программного решения по ответственности;
- создавать решение и проекты .NET 9;
- настраивать ссылки между проектами;
- организовывать каталоги `src`, `tests`, `docs`;
- применять `.gitignore` и `.editorconfig`;
- создавать понятную историю Git;
- документировать структуру решения;
- выполнять `dotnet build` и `dotnet test`.

## 3. Необходимое программное обеспечение

- .NET SDK 9;
- Git;
- VS Code, VSCodium или другая бесплатно доступная среда разработки;
- PowerShell/Bash;
- PlantUML или diagrams.net — по желанию для схемы.

## 4. Исходная задача

Необходимо подготовить структуру учебной системы **учета заявок технической поддержки**. На занятии оценивается прежде всего архитектура и организация проекта, а не полнота бизнес-функций.

Предлагаемые модули:

- `Support.Domain` — предметные сущности и правила;
- `Support.Application` — прикладные сценарии и контракты;
- `Support.Infrastructure` — технические реализации;
- `Support.WebApi` — HTTP-интерфейс;
- `Support.UnitTests` — модульные тесты.

## 5. Ход работы

### Этап 1. Создание репозитория — 25 минут

Создайте каталог проекта и инициализируйте Git:

```bash
mkdir SupportSolution
cd SupportSolution
git init
dotnet new gitignore
```

Создайте каталоги `src`, `tests`, `docs` и файл `README.md`.

В README укажите:

1. назначение решения;
2. используемую версию .NET;
3. команды сборки и тестирования;
4. краткое описание модулей.

### Этап 2. Создание решения — 35 минут

```bash
dotnet new sln -n SupportSolution
dotnet new classlib -n Support.Domain -o src/Support.Domain
dotnet new classlib -n Support.Application -o src/Support.Application
dotnet new classlib -n Support.Infrastructure -o src/Support.Infrastructure
dotnet new webapi -n Support.WebApi -o src/Support.WebApi
dotnet new xunit -n Support.UnitTests -o tests/Support.UnitTests
```

Добавьте проекты в решение:

```bash
dotnet sln add src/Support.Domain/Support.Domain.csproj
dotnet sln add src/Support.Application/Support.Application.csproj
dotnet sln add src/Support.Infrastructure/Support.Infrastructure.csproj
dotnet sln add src/Support.WebApi/Support.WebApi.csproj
dotnet sln add tests/Support.UnitTests/Support.UnitTests.csproj
```

### Этап 3. Настройка зависимостей — 35 минут

Разрешите следующие зависимости:

- Application → Domain;
- Infrastructure → Application и Domain;
- WebApi → Application и Infrastructure;
- UnitTests → Domain и/или Application.

Пример:

```bash
dotnet add src/Support.Application/Support.Application.csproj reference src/Support.Domain/Support.Domain.csproj
```

**Недопустимая зависимость:** Domain → Infrastructure.

В `docs/modules.md` создайте таблицу:

| Модуль | Ответственность | От чего зависит | Почему |
|---|---|---|---|

### Этап 4. Предметная модель — 35 минут

Создайте сущность заявки с идентификатором, заголовком и статусом:

```csharp
public enum TicketStatus
{
    New,
    InProgress,
    Closed
}
```

Добавьте правило изменения статуса. Бизнес-правило должно находиться в `Support.Domain`, а не в контроллере Web API.

### Этап 5. Контракт инфраструктуры — 30 минут

В Application создайте контракт:

```csharp
public interface ITicketRepository
{
    Task<SupportTicket?> GetAsync(Guid id, CancellationToken cancellationToken);
    Task SaveAsync(SupportTicket ticket, CancellationToken cancellationToken);
}
```

В Infrastructure реализуйте хранение в памяти. Объясните, почему интерфейс расположен выше технической реализации.

### Этап 6. Минимальный внешний интерфейс — 25 минут

Добавьте один endpoint Web API: создание или получение заявки. HTTP-слой должен преобразовывать входные данные и передавать управление прикладному коду, а не содержать основное предметное правило.

### Этап 7. Тестирование — 30 минут

Создайте минимум два xUnit-теста:

- успешный переход статуса;
- запрещенный переход.

Выполните:

```bash
dotnet build
dotnet test
```

Обе команды должны завершиться успешно.

### Этап 8. Git и документация — 25 минут

Сделайте не менее трех логических коммитов, например:

1. `Создана структура решения`;
2. `Добавлена предметная модель заявок`;
3. `Добавлены тесты и документация`.

Проверьте `git status` после сборки: `bin` и `obj` не должны отслеживаться.

## 6. Что предоставить преподавателю

- репозиторий проекта;
- README;
- `docs/modules.md`;
- исходный код пяти проектов;
- минимум два теста;
- вывод `dotnet build` и `dotnet test`;
- историю минимум из трех содержательных коммитов;
- краткий вывод о направлении зависимостей.

## 8. Контрольные вопросы

1. Чем решение `.sln` отличается от проекта `.csproj`?
2. Почему Domain не должен зависеть от Infrastructure?
3. Зачем отделять `src` и `tests`?
4. Какие файлы не следует хранить в Git?
5. Для чего нужен `.editorconfig`?
6. Почему интерфейс репозитория полезно отделять от его реализации?
7. Почему бизнес-логика не должна жить в контроллере?
8. Как доказать воспроизводимость проекта?
9. Почему несколько логичных коммитов удобнее одного большого?
10. Какие проблемы возникнут при циклических зависимостях модулей?

## 9. Вывод

Работа считается выполненной, если структура отражает ответственность модулей, проект собирается в .NET 9, тесты проходят, репозиторий не содержит лишних артефактов и другой разработчик может понять устройство решения по документации.
